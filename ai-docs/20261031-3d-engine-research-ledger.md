## R1 任意斜三角形：每次画一条深度相等的斜线

> 接着开发呗。其实我当时已经有任意三角形的构想了，现在我也回忆起来了。这个3dengine专门开一个科研记账。和2012年分开。
> 就是我在想的是每次画一条z=常数的斜线，然后用好的光栅化算法保证每次画的线中间不要有洞。……到时候交付物我希望是一个按照当时的knowledge cutoff的proof和伪代码。然后有任意斜的三角形之后摄像机就可以随意了，然后wishlist渲染实验室可以接图形引擎2026版。

- **题目**：2012 年的引擎只画得了竖直的墙和水平的地板，因为竖直的面「同一列深度相同」、水平的面「同一行深度相同」，一列或一行里贴图坐标随位置均匀变化，只要做加法。作者的构想是推广到任意斜面：面上深度相同的点连成一条线，沿这条线画，贴图坐标也是均匀变化的。
- **Claude 的读法（没证）**：
  - 斜面上「深度 = 某个常数」的点，是这个面和一个与屏幕平行的平面的交线，是一条直线，投到屏幕上还是直线；沿它深度不变，所以屏幕到贴图是一次函数，每条线只做一次除法。
  - 同一个面上所有这样的线方向都相同，而且都和屏幕平行，所以投到屏幕上**互相平行**（斜率一样，没有灭点）。于是整个三角形可以用一族平行斜线扫满。
  - 「中间不要有洞」：一族平行斜线沿短的那个方向每次挪一个像素，每条线用**同一个点阵模板**（同一套取整），相邻两条正好拼满、不重不漏。这是要证的那一条。
- **交付物（作者定的）**：一份证明 + 伪代码，按 2012 年的知识写：高中数学（相似三角形、直线方程、一次函数递推），不用矩阵和线性代数。知识范围由作者到时候给——Shader 实验室 README 10-27 那条同一件事：「只用 user 高中知识范围内的数学和做法，范围由 user 到时候给」「斜的面怎么切是 user 当年想过的一处」。
- **当年的知识边界**（作者 10-31「历史记账」）：「微元法就是贴皮的微积分，只是dx*dy会fomo不知道该丢罢了」「但是线性代数我是全量不会」。论文 3.1.5 的「微元」就是这个。
- **作者对推法的判断**（同日，没改交付物）：「不过三角形的算法我以一个负责任的成年人判断不用线性代数，用cpho的推法会非常痛苦。而且可能会miss一些合并优化空间」。
- **作者的理念**（同日）：「可能是因为我想省掉稀疏矩阵的几个0所以觉得展开形式才更接近物理和算力本源吧！线性代数是用空间来换复杂度的，哈哈哈！」——2012 年的代码确实没有一个矩阵：只能左右转，变换写成 2×2 的展开式；墙竖、地板平，「在面的哪一侧」退化成平面图上的直线方程。
- **之后**：有了任意斜三角形，相机就能随意转（现在只能左右转、抬头低头是上下挪地平线）。Shader 实验室的 wishlist 接图形引擎 2026 版。
- 推导方案见 R7（线性代数 vs 只想标量）。
- **模拟验证（10-31，Claude Opus 5.5）**：300 个随机三角形、21 万个像素，按「深度相等的斜线」画（每条线一次除法、线内只做加法），和逐点精确透视比：落在不同棋盘格的像素 4.77%，比精确算法自己把采样点挪半个像素（9.92%）还少；不做透视的贴法（PS1 式）59%。平均每条线 21 个点，也就是除法是逐点做法的 1/21。每个像素按「行号减模板偏移」唯一归到一条线，所以不漏不重（这条可以直接证）。脚本在任务临时目录 `e3d/tri_constz.py`，没进仓。
- 状态：数学上做得出（模拟证实）；历史准确版的证明 + 伪代码没写。

## R2 当年代码的优化空间

> 我还以为至少有几个float之类的常识错误可以优化。如果让你或者fable写咱们的优化空间还有多大。分low hanging fruit和全量fable。你可以把其他几个大人写的doom拉下来放放参考的地方对

- 题目：同一个场景、同一台机器，顺手改（不换算法）能快多少，换算法全量重写能快多少；拿别人在卡西欧上写的 3D 引擎 / Doom 移植对照。
- **怎么量的**（10-31，Claude Opus 5.5）：把当年的 `.h` 原样复制到临时目录，只在函数入口和最里层循环加计数器，电脑上用 gcc 编；照主循环画一帧（不读键、不显示），开局位置原地转一圈、32 个朝向，每帧数一遍。第一帧和网页版逐点一致（只差第 1 行两个调试点），所以数的是同一套代码。
- **每帧做了多少事**（平均 / 最多）：

  | 什么 | 平均 | 最多 | 说明 |
  |---|---|---|---|
  | 待画清单 | 15 项 | 38 项 | 墙 + 地板三角形 + 立牌 |
  | 世界 → 相机的坐标变换 | 414 次 | 1,246 次 | 场景只有 35 个点：两两比较时同一个点反复重算 |
  | 屏幕列范围 / 直线方程 | 77 / 30 次 | 286 / 92 次 | 同上，每次比较现算 |
  | 两两比较 | 232 次 | 898 次 | 真正比到要交换的 2 次 |
  | 画墙的点 | 4,804 | 6,540 | 每列 1 次浮点除法，共 235 列 |
  | 画地板三角形的点 | 1,752 | 4,785 | |
  | 铺地面的点 | 3,937 | 3,937 | **真写进缓冲的只有 37 个**：格子图大半是空地形，白算 |
  | 画立牌 + 手里的东西的点 | 6,335 | 9,737 | 真写 2,396 个；手里的东西缩放永远是 1，也逐点缩放 |

- **结论（Claude 的读法）**：
  - 核心算法当年已经对了：每列 / 每行一次除法（透视正确），最里层只有整数加法和移位。拿检疫桶 `casio-3d-refs` 里别人的引擎比：多数用 double 做矩阵、只平涂不贴图；贴图做得最全的 VIMS3D（2026）在透视正确模式下**每个点**一次除法。
  - 浪费在「胶水」上。**顺手改（low hanging fruit，不换算法）**：
    1. 每帧每个点只变换一次（414 → 35），每一项的屏幕列范围和直线方程也只算一次存起来。
    2. 铺地面只扫有地形的那几格投到屏幕上的范围（3,937 → 几十）。
    3. 手里的东西换成排好的小图按字节贴，一次 8 个点（6,335 次逐点缩放 → 几百次字节操作）。
    4. 灰度关着时不写亮层：现在每个写出的点读三层贴图、写两块缓冲，显示只用暗层。
    5. 浮点常量带上 `f`：`0.05`、`0.0001`、`64.5` 在 C 里是 double，比较和加法会升成双精度软件运算（要看当年的编译选项，没核）。
    6. 缓冲拷贝逐字节 → memcpy；`Render()` 每帧重算 `sinf` / `cosf`。
    估计快 1.5–3 倍（没量）。
  - **全量重写（Fable 级，换算法）**：
    1. 浮点归零：坐标变换、每列每行那次除法全换定点数 + 倒数表。
    2. 从近到远画 + 屏幕列覆盖表（论文的一维集合算法、Doom 记「哪些列已满」同一类）：墙的每个点只画一次，被挡住的不算；每帧的两两比较换成关卡预处理（BSP 或分区）。
    3. 直接写显存；墙按列画进按列存的缓冲，最后转一次；立牌预缩放几档按字节贴。
    4. 可选：最里层写汇编。
    估计快 4–10 倍（更没量）。省出来的时间可以花在 R1 的任意斜三角形或灰度上。
- **为什么一个点变换那么多次**（作者 10-31）：「我之前说不用线性代数的后果的直觉，只能按照物理语义一步一步做」「反正现在你有sympy了」。读法：线性代数的习惯是先把所有顶点一次性变到相机空间（一个矩阵乘一整个顶点数组），后面全用变好的；按物理语义一步步做，变换就挂在「处理某一项」上，同一个点每被比较一次就重算一次。核心循环当年是手工化简的。
- **sympy 核了当年手推的公式**（10-31，`~/venvs/pytorch` 里的 sympy 1.14）：画墙的 u = A/B、换列时 A 减 Z1 / B 加 dZ、这一列深度 = C/B（深度的倒数沿列线性）、墙顶第 D 行每列加 E、列内贴图行号随屏幕行线性（M += N），画地板的 u、v 两组系数 fA…fF——**9 条全对**。顺带看到：地板按像素中心算（64.5），墙和顶点投影按 64，差半个像素，看不出来。
- **「外国大人写的更流畅」**（作者 10-31「但是我记得外国大人写的比我流畅啊，但也许我只是看视频没有实机测过」）：检疫桶里能看的演示动图（Viliami 那两个）是在电脑上的官方模拟器里录的（画面里有鼠标指针、模拟器窗框），场景是一个立方体线框、一片格子地板，每帧几十条线、不贴图。模拟器的速度不等于真机，工作量也比满屏贴图小一两个数量级。要比得在同一台真机上量。
- **SH3 指令数**（10-31，sh-elf-gcc 14.1 `-m3 -O2` 编当年的 `.h`，数汇编）：画墙最里层一个不透明像素 29 条指令。每帧像素循环约 1.7 万次 ≈ 50 万条指令；论文的一帧 110 毫秒 ≈ 320 万周期（29.5 MHz）。**推断**：像素循环只占五分之一左右，其余约五分之四在外围（每帧约 1.2 万次软件浮点、双精度提升、显示等）。编出来的代码里确实有双精度调用（`__extendsfdf2`、`__gtdf2`、`__adddf3`），GCC 按 C 的规矩把 `0.05` 这类常数当 double；当年卡西欧编译器的选项不知道。软件浮点一次走多少条指令没量（libgcc 里加法函数全长 705 条，不等于一次走过的路），要 SH 模拟器实跑。
- **整理成报告**：`20261031-3d-engine-2012-performance.md`（每帧计数、SH3 指令数、时间分配、浪费在哪、三档能快多少）。测算脚本在 `2026/research/`。
- 状态：计数是量的，倍数是推断（顺手改约 2 倍、加外围定点化 3–5 倍、全量重写 5–10 倍，前提是外围确实占大头）。真要量倍数，用 R4 的工具链编出来，在真机或指令模拟器上计时。

## R3 1-Bit Jam：白面黑线的线框 + 背面消隐

> 冲1bit jam的话还有一个思路是sunset 图形引擎，做一个渲染实验室里面的带背面消隐的线框，这个9750gii接得住吗，会不会反而更快。你帮我前期科研一下。是不是非得要深度缓冲。

> 最好是好看的那种不是全量线框的，catsup里面有更新版的。但是只要效果一致就行，不一定要用他们的算法

- **要的效果** = CatsUp 的线稿（CatsUp `ai-docs/20261030-silhouette-outlines.md`）：白色的面、黑色的线，被挡住的线不画；硬边看得见就画；软边只在它正好是外轮廓时画（两侧的面一个朝镜头、一个背镜头）；外轮廓可以加粗；两个物件穿插的交线不画（SketchUp 同款）。Shader 实验室的「卡西欧 · 线稿」是同一路的 1-bit 版本。
- **结论（Claude 的推理，没写代码、没量）**：
  - **不用深度缓冲。**
    - 面朝不朝镜头 = 投到屏幕上的三个点是顺时针还是逆时针（整数叉乘的正负）；背着的面不画。
    - 哪条边画：硬边 = 两侧至少一面朝镜头；软边 = 两侧一正一反（就是外轮廓，和 CatsUp 同一条判法）；开口的边 = 总画。
    - 被挡的线：从远到近，每个面先涂白、再描它要画的边。近的面涂白时自然盖掉后面的线——「白面黑线」本身就是这么画的。
    - 远近顺序：一个物件里凸的部分只靠背面剔除就对；多个物件按物件排序；面互相穿插、排不出顺序的，设计关卡时避开（论文当年也这么做），或者退回深度缓冲。
  - **深度缓冲放得下，但没必要**：16 位 × 128 × 64 = 16 KB；卡西欧 SDK 文档写的是全局变量最多 8 KB、堆 48 KB（VIMS3D 在老机型上就 malloc 了 32 KB 当深度缓冲）；每个点都要算深度、比深度，更慢；交线本来就不画。
  - **小屏要注意的**（Shader 实验室的「卡西欧 · 线稿」也这么处理）：投影后很小的面不描边，不然糊成一团；外轮廓 2 像素、内部硬边 1 像素，到时候调。
  - **快不快（估计）**：涂白是整字节清零，一次 8 个点；画线逐点。几十个面的场景每帧大约几万个处理器周期，当年的贴图引擎每帧 110 毫秒（约 320 万周期），快一个数量级以上，帧率会先被液晶刷新卡住。
  - **验证**：同一个模型，CatsUp 线稿渲成 128×64 和计算器出图逐点对比（像塔防截图那样对拍）。
- **原型**（10-31，Claude Opus 5.5；`2026/research/lineart_proto.py`，Python，不是计算器代码）：128×64、1-bit，房子 + 坡顶、16 面圆柱、箱子；背面剔除 + 从远到近先涂白再描边，硬边看得见就画、软边只在外轮廓画、很短的内部边不画；视野 40°（CatsUp 默认）。出图 `2026/research/lineart-front.png`、`lineart-three-quarter.png`：被挡的线不画（箱子挡住圆柱左下角）、圆柱侧面中间没有竖线、外轮廓和屋脊画了。和 CatsUp 渲出来的逐点对比还没做。
- **小红帽试跑**（10-31，作者「其实你可以跑一下小红帽。贴图你想办法二值化一下。不过也许小红帽会爆内存？有256+ tri」；模型 = 作者私仓的 littlered-pose1，图和脚本也只留私仓）：275 个顶点、291 个三角形、一张 256×256 贴图，这个角度朝镜头的 155 个。
  - **内存不会爆**（估算）：模型数据（顶点约 3.3 KB、贴图坐标约 1.1 KB、索引约 1.7 KB）和贴图（1-bit 8 KB / 灰度 64 KB）都是常量，放闪存；每帧要的内存——变换后的顶点约 4.4 KB、三角形排序约 1.2 KB，加深度缓冲也只多 16 KB——远小于 48 KB 的堆。会爆的是 2012 原样版：待画清单写死 100 项，而且只认墙和地板。
  - **贴图 1-bit 花了**：贴图预先抖动成 1-bit、或保留灰度在屏幕上抖动，两种都认不出人——浅色的地方融进背景、整个人化成噪点。实证了作者「这么小的屏贴图会花」。
  - **线稿认得出是个人**，但头部的线太密（兜帽、头发挤成一团），要调：硬边的角度阈值提高，或者短边剔得更狠。
- 状态：效果原型有了，等作者看图；计算器上的版本没写。

## R4 工具链

> 有开源的sdk当然要用，你就可以验证了。然后官方的我onedrive里面应该有备份。不过我估计你更喜欢开源的

- 定了：用开源的 fxSDK（gint）编真机 G1A；卡西欧官方 SDK 作者那边有备份，需要时再拿。魔塔「只带用到的字」那条验证（`wishlist.md`）用同一套。
- 这台机器装得起来、不用 sudo：gcc 的脚本自己带 gmp / mpfr / mpc；缺的 libusb 从源码静态编；fxconv 要的 PIL 装进单独的 Python 环境。
- **fxSDK 不带模拟器**：它只编出真机的 G1A。量速度要么真机跑，要么另编 GNU 的 SuperH 指令模拟器（binutils-gdb 里的 sim），要么用官方 SDK 自带的模拟器（Windows）。哪个计时准还没查。
- **装好了**（10-31）：fxSDK + binutils 2.42 + gcc 14.1 + OpenLibm + fxlibc + gint，装到 `~/.local`（`fxsdk`、`sh-elf-gcc` 在 `~/.local/bin`）；fxconv 要的 PIL 在 `~/venvs/20261031-fxsdk`；这台机器没有 texinfo，用一个只造空文件的假 makeinfo 跳过说明书。用 fxSDK 模板 `fxsdk new` + `fxsdk build-fx` 编出 24,964 字节的单色机 G1A，文件头对。整套编下来约 6 分钟。
- **当年的源码不能直接编**：魔塔、3D 引擎调的是卡西欧官方 SDK 的库（fxlib：画屏、读键、读写文件、定时器），那是官方编译器的格式，GCC 链接不了。用 fxSDK 编当年的源码，得先把这些调用换成 gint 的（或者写一层替身，像网页模拟器那样）——这本身就是 2026 版的活。
- 状态：装好了；还没写真机上跑的东西。

## R5 9750GII 刷 9860 系统：硬件上缺什么

> 9750gii刷机9860可能缺元件，你调查一下，科研记账
> 9750我已经亚马逊下单了。到时候有真机grounding

- **查到的**（10-31，Claude Opus 5.5；网页 + 存下来的 cnCalc 帖子）：

  | 项 | 结论 | 出处 |
  |---|---|---|
  | 背光 | 9750GII 没有背光硬件，刷了 9860 系统也不亮，事后加不了 | Planète Casio 维基 Fx-9750GII；cnCalc 6553 帖（路人，2011-08-13）「升级后，背景灯，初始化对比度，sd菜单读内存都不会有效」；作者 2011-01-11（cnCalc 5348 帖）「9750gii与9860gii好像只少了一盏背光灯！」 |
  | SD 卡 | 没有（9860GII 也只有 SD 版带卡槽） | 维基 |
  | 存储内存（闪存） | 芯片和 9860GII 一样，9750GII 原装系统不用它；刷 9860 系统后能用（魔塔的字库就放在这里） | 作者 2011-01-11「两者flash（永久闪存storage memory）是一样的……只是9750gii的os无法调用flash，而9860gii可以调用」 |
  | 内存 | 64 KB，两台一样 | 维基；cnCalc 24689 帖（9750GIII / 9860GIII 拆机） |
  | 处理器 | 早期 fx-9750GII-1 = SH3，深蓝外壳白键盘框；后期 fx-9750GII-2 = SH4a，白外壳深蓝键盘框。看 Memory 应用里的系统版本号：2.01 及以前大概是 SH3，2.02 及以后是 SH4。刷机要按处理器选对系统镜像，选错会变砖 | 维基；中文刷机博客（blog.iyatt.com：版本号末位 0 = SH3、1 = SH4） |

  | 时钟晶振（实时时钟） | **没找到来源**：没查到 9750GII 少焊时钟晶振的说法，也没查到它的实时时钟不走。要真机核 | — |
  | 「只能装 4 个 add-in」 | 不是硬件：作者 2012-02（cnCalc 7167 帖）遇到过，备份、重置、整理内存后好了；别人的 9750 刷 9860 装了十几个 | 7167 帖 |

- **真机到了要核的**（作者 10-31 在亚马逊下了单）：
  1. 型号和处理器：外壳颜色 + Memory 应用里的系统版本号。现在卖的多半是 fx-9750GIII（2020 年起，SH4a）〔推测，到货看〕，和 2012 年那台 SH3 不一样：2012 年的 G1A 当年在 SH4 的新机上就跑不起来（7735 帖「新版9860不能用」）。GIII 能不能直接装 add-in、要不要刷机，到货核。
  2. 用 R4 的 fxSDK 编一个「硬件探针」G1A：实时时钟走不走（隔几秒读两次计数）、主频（实时时钟和定时器对照）、显示一帧要多久、malloc 最多能要多少。
  3. 用探针的数校网页模拟器的速度：BASIC 每秒 600 行、3D 引擎每帧 110 毫秒，现在都是估的或从论文抄的。
- 状态：查了；时钟晶振和速度等真机。

## R6 硬件全量 exploit

> 对我当时不会肝硬件所以质感用大人写的魔法库。这个你现在应该能全量exploit出来

- **题目**：2012 年的引擎通过现成库（卡西欧 fxlib + Revolution-FX）碰硬件：画面先画进自己的两块缓冲、再交给库显示；变量只敢开在 8 KB 的全局区。2026 年用 gint（开源的卡西欧内核库，直接管硬件）能用上的：
  - **内存**：卡西欧 SDK 文档写全局变量最多 8 KB、堆 48 KB；VIMS3D 在 SH4 机型上还借芯片里 16 KB 的 DSP 内存当深度缓冲（地址 0xfe200000）。
  - **显示**：直接写显存，自己决定什么时候送屏（gint 单色机上怎么送屏、快多少，没核）。
  - **灰度**：定时器驱动的两块缓冲轮流显示（2 位灰度），当年注释掉的 `GrayInit` 那条路。
  - **超频**：SH4 机型（SH7305）可以改时钟倍频，Casiomania（Revision 2026 的 demo）就这么做。2012 年论文的演示开的是 2 倍。
  - **计时**：硬件定时器，精确到能锁帧算 dt（Doodle Jump 2026 版在网页上已经这么做）。
- **注意**：gint 对最早的 SH3 机型只是部分支持；作者 10-31 新下单的那台多半是 SH4a（见 R5）。
- 状态：开题，没做；真机到了先跑 R5 的探针，知道这台机器的底。

## R7 推导方案：线性代数 vs 只想标量（sympy 全量化简）

> 我们到时候可以考虑线性代数和sympy全量化简只想scalar两个方案

- **方案甲：线性代数。** 顶点数组一次乘矩阵变到相机空间；面用法向量、平面方程；三角形用重心坐标或边函数。作者 10-31 的判断：不用线性代数推三角形「会非常痛苦。而且可能会miss一些合并优化空间」。
- **方案乙：只想标量。** 照 2012 年的写法，按物理语义一步步写展开式；推导和化简交给 sympy（10-31 已经用它核过当年 9 条公式，见 R2），由它找能合并的项、把每个点的运算压到只剩加法。作者的理念：「展开形式才更接近物理和算力本源」「线性代数是用空间来换复杂度的」。
- 两个方案最后落到计算器上的都是标量代码（SH 处理器没有向量指令），区别在推导时用什么语言想、谁来找合并的机会。
- 〔Claude 提议，没拍〕两条路推出同一个三角形的递推式，用 sympy 判断是不是恒等，互相对拍。
- **拍了**（作者 10-31）：「其实我想的是两边好处都拿，2026版科研可以全量数学工具」「只有那个三角算法先历史准确看能不能弄出来圆梦，然后2026版我们就正常优化了」——三角形算法先按 2012 年的知识做出来；2026 版正常优化，全量数学工具（线性代数 + sympy）都用。
- 状态：方向拍了；没开工。
